## Foundation Contract

The published shape of this foundation. It is built before every other foundation: a web server,
a database, or a CLI is built *into* this tree, this environment, and this test runner. Carried
verbatim into `go_compact.md`.

- source_root: internal/
- test_command: go test ./...
- environment: the module declared in `go.mod`; no vendored toolchain
- dependencies: `go.mod`

```
project/
  go.mod                  # module path; the Go toolchain version
  cmd/                    # one directory per binary, each package main
  internal/               # application packages; not importable outside this module
  bin/                    # launchers; each runs the toolchain, never a vendored copy
```

Application foundations add packages under `internal/`. The generated persistence library is a
separate module at `persistence/`, linked by the root `go.mod`.

### Native application layouts and fixtures

Initialize the root `go.mod` in the language foundation before the DATABASE block.
Use `cmd/app/main.go` for process startup, `internal/cli` for CLI behavior, and
`internal/appserver` for HTTP behavior. The root application module requires
`drydock.local/persistence v0.0.0` with `replace drydock.local/persistence => ./persistence`;
the generated persistence directory owns its nested module. Run both module test suites.

For a CLI, expose `Run(args []string, stdout, stderr io.Writer) int`, use a local
`flag.FlagSet` with `flag.ContinueOnError`, and test with `bytes.Buffer`. Only main calls
`os.Exit`. For HTTP, expose `NewHandler(...) http.Handler` using `net/http.ServeMux`.
Use `httptest.NewRecorder` and `httptest.NewRequest` for handler tests, or
`httptest.NewServer` with `t.Cleanup(server.Close)` when testing a real HTTP client.
Keep business logic in application packages and persistence access in the shipped library.

### How do we execute and measure Acceptance Criteria in this language?

An Acceptance Criterion (AC) is an executable check of Blueprint-required behavior. Native tests
use `testing` in `*_test.go`; the project gate is `go test ./...`. Within the existing Blueprint
Python AC container, execute a named test through the shipped helper:

```python
from drydock_go import run_test
result = run_test("./internal/orders", "TestCreateOrder")
assert result.passed, (result.status, result.stdout, result.stderr)
```

Drydock stages this helper beside the criterion. It runs `go test -json -count=1 -run` with an
exact test name, retains output and per-test outcomes, and rejects absent/skipped tests as proof.
The enclosing AC provides identity, timeout, result storage and repair state. Compilation errors
remain distinct from assertion failures in `result.status`. Coverage and persistence observations
require explicit instrumentation per criterion; unavailable observations are unknown.

A criterion that exercises the command line runs the built executable through the same helper,
never `go run`, which reports every non-zero program exit as 1:

```python
from drydock_go import cli_runner
code, out, err = cli_runner("--top", "0", "data.csv")
assert code == 2, (code, out, err)
```

`cli_runner` builds the single `./cmd/<name>` main package once with `go build` and returns
`(exit_code, stdout, stderr)`; pass `package="./cmd/<name>"` when there are several, and `input=`
for standard input. A failed build settles the criterion as `execution-error`.

### How does this language provide the shared persistence contract?

Use the shipped module in `Rigging/languages/go/persistence/`. Drydock copies it to the Target's
`persistence/`, generates `schema.go`, `testing.go` and a schema command from `DATABASE.md`, and
links it into the existing root `go.mod` as `drydock.local/persistence`. Driver versions and sums
are shipped; SQLite uses `go-sqlite3` (a C compiler and CGO are required), PostgreSQL uses `lib/pq`.
Run `go mod download` during dependency provisioning; execution requires these modules available.

Call `persistence.OpenDatabase(ctx, dsn)`, then typed methods such as
`db.Tickets.List(ctx, persistence.TicketsListInput{Status: "open"})`. Methods return a value and
an error. Optional inputs use pointers; read results are generated structs. Undeclared operations
and unsupported field types fail explicitly. Use `OpenSession(ctx, dsn)` for native database criteria;
empty DSN selects the configured, provisioned application store. Defer its cleanup and check the
returned error: it rolls back on success and failure, never applies schema or deletes the store.
Pass the same Store to the feature. Other connections and external effects require committed,
idempotent criteria with owned records and supported cleanup. Both engines retain autocommit
outside explicit rollback scopes.

The Go library and generator are verified on SQLite and PostgreSQL. Keep application SQL inside
the library; agents write callers. The language foundation must create `go.mod` before the
DATABASE step. Python Blueprint AC containers invoke the native Go tests through `run_test`.

# FEATURE: CSV Reading

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Read UTF-8 RFC 4180 CSV with the first record as the header, recording each record's source line. |
| Depends On  | ARCHITECTURE.md |
| Provides    | csvdata.Read |
| Consumes    | None |

## Purpose

`internal/csvdata` turns an input stream into a header and data records. Trimming, null recognition, and
rejection of malformed input are separate stories that build on this reader.

## Behavior

- `Read(r io.Reader) (*Table, error)` parses with `encoding/csv`, with `FieldsPerRecord = -1` so field
  counts are judged by the rejection story, and `LazyQuotes` off.
- `Table` has `Header []string` and `Records []Record`. `Record` has `Line int`, the 1-based source line
  on which the record starts, and `Fields []string`.
- The first record is the header; every later record is a data record. Values are returned as parsed
  with no trimming.
- A quoted field containing a comma is one value. A quoted field may contain doubled quotes and newlines.
- A line ending after the last record creates no extra record. Input with or without a final newline
  yields the same records.
- Input with no record at all (empty or only blank lines) returns a `Table` with a nil `Header` and no
  `Records` and no error; the input-rejection story turns that into a rejection.
- A syntax error reported by `encoding/csv` is returned wrapped so callers can recover the line number
  with `errors.As` and `*csv.ParseError`.
- `Read` does not open files; `cli` opens the file and passes the reader.

## Tests For The Project Suite

The builder writes these `internal/csvdata` tests, named exactly as listed:

- `TestReadHeaderAndRecords`: header is the first record; the rest are data records.
- `TestReadQuotedComma`: a quoted field with a comma is a single value.
- `TestReadTrailingNewline`: a final newline adds no record, matching the same input without one.
- `TestReadRecordLineNumbers`: each record carries the line on which it starts, including after a
  quoted field that spans lines.
- `TestReadHeaderOnly`: a header with no data yields zero records.
- `TestReadNoRecords`: empty input yields a nil header and no records.

# FEATURE: Trimming

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Trim leading and trailing spaces from every header name and every value before any other rule applies. |
| Depends On  | FEATURE-CsvReading.md |
| Provides    | csvdata.Trim |
| Consumes    | csvdata.Read |

## Purpose

Every header name and every value is trimmed of leading and trailing spaces before null recognition,
typing, counting, or comparison. Padded text such as `  Globex  ` and `Acme Corp ` therefore count as
`Globex` and `Acme Corp`.

## Behavior

- `Trim(t *Table)` replaces, in place, each header name and each record field with the same string
  stripped of leading and trailing space characters (U+0020).
- Only U+0020 is trimmed. Tabs and other whitespace are preserved. Interior spaces are preserved.
- Trimming applies after CSV parsing, so spaces inside a quoted field are also trimmed.
- Record line numbers and field counts are unchanged.
- The cli pipeline calls `Read` then `Trim` before any other rule; the profile-output and
  frequency-mode stories wire that call.

## Tests For The Project Suite

The builder writes these `internal/csvdata` tests, named exactly as listed:

- `TestTrimHeaderNames`: padded header names are trimmed.
- `TestTrimValues`: padded values are trimmed on both sides.
- `TestTrimQuotedPadding`: spaces inside a quoted field are trimmed, and the comma inside the quotes is kept.
- `TestTrimOnlySpaces`: tabs are preserved and interior spaces are kept.
- `TestTrimKeepsLines`: line numbers and field counts are unchanged.

# FEATURE: Null Values

## Purpose

Statistics, type inference and frequency counting all need one shared definition of "null". This
feature provides it as a function in `internal/csvdata` so no other package re-implements it.

## Behavior

- `func IsNull(value string) bool` in package `csvdata` receives a value that has already been
  trimmed of leading and trailing spaces.
- A value is null when it is the empty string, or equals `NA`, `N/A`, or `NULL` ignoring case

  an input (trimming precedes this rule), so only exact spellings match.
- A quoted empty field (`""`) is read by `encoding/csv` as an empty string, so it is null.
- A field made only of spaces is empty after trimming and is therefore null.
- `IsNull` is pure: it never reads files and never allocates state.

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |

| Depends On  | FEATURE-NullValues.md |
| Provides    | profile.InferType (integer, number) |
| Consumes    | csvdata.IsNull |

## Purpose

Column typing decides which statistics apply. This feature starts `profile.InferType` in
`internal/profile` with the two numeric types. Later features extend the same function with
`date`, `boolean`, `text`, and `empty`.

## Behavior

- `func InferType(values []string) string` in package `profile` receives the trimmed values of one

  fallback `text` until later features add the remaining types.

# FEATURE: Arguments

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Parse csvstat options and exactly one file argument, with options preceding the file. |
| Depends On  | FEATURE-Executable.md |
| Provides    | cli.ParseArgs |
| Consumes    | cli.Run |

## Purpose

csvstat accepts two command forms:

```text
csvstat [--column <name>] <file>
csvstat --freq <name> [--top <n>] <file>
```

Options precede the file and exactly one file is required. This story delivers the parser and its
wiring into `Run`. Cross-option validation (`--top` without `--freq`, `--column` with `--freq`,
non-positive `--top`) belongs to the usage-errors story.

## Behavior

- `internal/cli` exports `ParseArgs(args []string) (Options, error)`.
- `Options` has fields `Column string`, `Freq string`, `Top int`, `TopSet bool`, `File string`, and
  flags are recorded as set or not set (a presence flag for `--column` and `--freq`, so an empty value
  is distinguishable from an absent option).
- Parsing uses a local `flag.FlagSet` created with `flag.ContinueOnError` and its output discarded.
  Options take a separate value (`--top 3`); a repeated option is a parse error.
- Parsing stops at the first non-option argument. That argument is the file. Any argument after it,
  including a later option, is an extra argument and a parse error. Options after the file are
  therefore rejected.
- A missing file, an extra argument, an unknown option, and an option with no value each return an
  error. `--top` is parsed as a decimal integer; a non-integer value is a parse error.
- `Run` calls `ParseArgs`. When it returns an error, `Run` writes one line to `stderr`, writes nothing
  to `stdout`, and returns 2.

- `TestParseArgsFileOnly`: `[file]` yields File set and no options.
- `TestParseArgsColumn`: `[--column name file]` yields Column and File.
- `TestParseArgsFreqTop`: `[--freq name --top 3 file]` yields Freq, Top 3, TopSet, and File.
- `TestParseArgsMissingFile`: `[--column name]` is an error.
- `TestParseArgsExtraFile`: two files is an error.
- `TestParseArgsUnknownOption`: `[--frobnicate file]` is an error.
- `TestParseArgsMissingValue`: `[file-less --top]` forms with no value are an error.
- `TestParseArgsOptionsAfterFile`: `[file --column name]` is an error.

# FEATURE: Input Rejection

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Reject empty files, blank-only files, empty or repeated header names, and ragged records with exit 3. |
| Depends On  | FEATURE-Trimming.md, FEATURE-CsvReading.md, FEATURE-Arguments.md |
| Provides    | csvdata.ErrRejected |
| Consumes    | csvdata.Read, cli.ParseArgs |

## Purpose

Malformed input must never produce partial output. Rejection is detected in `internal/csvdata`
and mapped to exit code 3 by `internal/cli`.

## Behavior

- `csvdata` exposes a rejection error type (sentinel or typed error matched with `errors.Is` /
  `errors.As`) named `ErrRejected`. For a ragged record it carries the 1-based line number.
- The file is rejected when:
  - it is empty (zero bytes);
  - it contains only blank lines;
  - any header name is empty after trimming;

- A header-only file is valid and yields zero data records.
- A trailing line ending after the last record creates no extra record.
- `cli.Run` reads the file named by the parsed arguments. On a rejection error it writes nothing
  to standard output, writes one diagnostic line to standard error naming the file (and the line
  number for a ragged record), and returns exit code 3.
- A CSV syntax error from `encoding/csv` (for example a bare quote) is also a rejection, exit 3.
