## Foundation Contract

The published shape of this foundation. It is built before every other foundation: a web server,
a database, or a CLI is built *into* this tree, this environment, and this test runner. Carried
verbatim into `go_compact.md`.

- source_root: internal/
- test_command: go test ./...
- environment: the module declared in `go.mod`; no vendored toolchain
- dependencies: `go.mod`

```
project/
  go.mod                  # module path; the Go toolchain version
  cmd/                    # one directory per binary, each package main
  internal/               # application packages; not importable outside this module
  bin/                    # launchers; each runs the toolchain, never a vendored copy
```

Application foundations add packages under `internal/`. The generated persistence library is a
separate module at `persistence/`, linked by the root `go.mod`.

### Native application layouts and fixtures

Initialize the root `go.mod` in the language foundation before the DATABASE block.
Use `cmd/app/main.go` for process startup, `internal/cli` for CLI behavior, and
`internal/appserver` for HTTP behavior. The root application module requires
`drydock.local/persistence v0.0.0` with `replace drydock.local/persistence => ./persistence`;
the generated persistence directory owns its nested module. Run both module test suites.

For a CLI, expose `Run(args []string, stdout, stderr io.Writer) int`, use a local
`flag.FlagSet` with `flag.ContinueOnError`, and test with `bytes.Buffer`. Only main calls
`os.Exit`. For HTTP, expose `NewHandler(...) http.Handler` using `net/http.ServeMux`.
Use `httptest.NewRecorder` and `httptest.NewRequest` for handler tests, or
`httptest.NewServer` with `t.Cleanup(server.Close)` when testing a real HTTP client.
Keep business logic in application packages and persistence access in the shipped library.

### How do we execute and measure Acceptance Criteria in this language?

An Acceptance Criterion (AC) is an executable check of Blueprint-required behavior. Native tests
use `testing` in `*_test.go`; the project gate is `go test ./...`. Within the existing Blueprint
Python AC container, execute a named test through the shipped helper:

```python
from drydock_go import run_test
result = run_test("./internal/orders", "TestCreateOrder")
assert result.passed, (result.status, result.stdout, result.stderr)
```

Drydock stages this helper beside the criterion. It runs `go test -json -count=1 -run` with an
exact test name, retains output and per-test outcomes, and rejects absent/skipped tests as proof.
The enclosing AC provides identity, timeout, result storage and repair state. Compilation errors
remain distinct from assertion failures in `result.status`. Coverage and persistence observations
require explicit instrumentation per criterion; unavailable observations are unknown.

A criterion that exercises the command line runs the built executable through the same helper,
never `go run`, which reports every non-zero program exit as 1:

```python
from drydock_go import cli_runner
code, out, err = cli_runner("--top", "0", "data.csv")
assert code == 2, (code, out, err)
```

`cli_runner` builds the single `./cmd/<name>` main package once with `go build` and returns
`(exit_code, stdout, stderr)`; pass `package="./cmd/<name>"` when there are several, and `input=`
for standard input. A failed build settles the criterion as `execution-error`.

### How does this language provide the shared persistence contract?

Use the shipped module in `Rigging/languages/go/persistence/`. Drydock copies it to the Target's
`persistence/`, generates `schema.go`, `testing.go` and a schema command from `DATABASE.md`, and
links it into the existing root `go.mod` as `drydock.local/persistence`. Driver versions and sums
are shipped; SQLite uses `go-sqlite3` (a C compiler and CGO are required), PostgreSQL uses `lib/pq`.
Run `go mod download` during dependency provisioning; execution requires these modules available.

Call `persistence.OpenDatabase(ctx, dsn)`, then typed methods such as
`db.Tickets.List(ctx, persistence.TicketsListInput{Status: "open"})`. Methods return a value and
an error. Optional inputs use pointers; read results are generated structs. Undeclared operations
and unsupported field types fail explicitly. Use `OpenSession(ctx, dsn)` for native database criteria;
empty DSN selects the configured, provisioned application store. Defer its cleanup and check the
returned error: it rolls back on success and failure, never applies schema or deletes the store.
Pass the same Store to the feature. Other connections and external effects require committed,
idempotent criteria with owned records and supported cleanup. Both engines retain autocommit
outside explicit rollback scopes.

The Go library and generator are verified on SQLite and PostgreSQL. Keep application SQL inside
the library; agents write callers. The language foundation must create `go.mod` before the
DATABASE step. Python Blueprint AC containers invoke the native Go tests through `run_test`.

# FEATURE: Usage Errors

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Reject malformed command-line arguments with exit status 2 and a single usage line on standard error. |
| Depends On  | FEATURE-Arguments.md |
| Provides    | exit code 2 |
| Consumes    | cli.ParseArgs |

## Purpose

Malformed invocations exit 2, write nothing to standard output, and write one diagnostic line to
standard error that shows the two command forms:

```text
csvstat [--column <name>] <file>
csvstat --freq <name> [--top <n>] <file>
```

## Behavior

Exit 2 for each of:

- no file argument
- more than one file argument
- an unknown option
- an option given without its value
- `--top` that is not a positive integer (zero, negative, or non-numeric)
- `--top` without `--freq`
- `--column` together with `--freq`
- a repeated option

Usage errors are decided from the arguments alone, before the file is opened, and exit 2 even when
the file exists and is valid.

## Programmatic Acceptance

=== AC usage-errors-exit-two ===
Intent: Every malformed argument form exits 2 and writes nothing to standard output.
Requires: executable=go; scope=test

import csv
import os
import tempfile
from drydock_go import cli_runner

rows = [["qty", "sensor"], ["1", "east"], ["2", "west"]]
with tempfile.TemporaryDirectory() as d:
    path = os.path.join(d, "in.csv")
    other = os.path.join(d, "other.csv")
    for p in (path, other):
        with open(p, "w", newline="", encoding="utf-8") as f:
            csv.writer(f, lineterminator="\n").writerows(rows)

        [],
        [path, other],

        ["--freq", "sensor", "--top", "-1", path],
        ["--freq", "sensor", "--top", "abc", path],
        ["--top", "3", path],
        ["--column", "qty", "--freq", "qty", path],

    for args in cases:

## Purpose

`csvstat --column <name> <file>` writes the profile header and only the row for the named column.

## Behavior

- The output has the same header and the same row content for that column as the full profile.
- The name is matched exactly and case-sensitively against the trimmed header.
- A name not present in the header exits 3 with empty standard output.
- Rejected input (ragged, empty, bad header) exits 3 with empty standard output.
- `--column` combined with `--freq` is a usage error (exit 2), owned by the usage-errors story.

# FEATURE: Failure Diagnostics

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Ensures every failing csvstat command writes nothing to standard output and exactly one diagnostic line to standard error. |
| Depends On  | FEATURE-InputRejection.md, FEATURE-UsageErrors.md, FEATURE-ProfileOutput.md |
| Provides    | stderr diagnostics, exit code 3 |
| Consumes    | csvdata.ErrRejected, cli.Run |

## Purpose

A command that fails reports the failure on standard error as one line and leaves standard output empty. Rejected input exits 3. The diagnostic names the file and, for a rejected record, its line number. Standard error is never compared by the grader, so its wording is free; its shape (one line, nothing on standard output) is the contract.

## Behavior

- Rejected input (empty file, file containing only blank lines, empty header name, repeated header name, ragged record) exits 3.
- Standard output is written only after the whole result is built, so no partial output precedes a failure.
- Exactly one non-blank line is written to standard error per failure.
- A ragged record's diagnostic includes the line number of the offending record.
- Exit code 1 (unreadable file) and exit code 2 (usage) share the same stdout-empty, one-line-stderr rule and are owned by their own stories.

# FEATURE: Unreadable File

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Exits 1 with an empty standard output when the named file cannot be opened or read. |
| Depends On  | FEATURE-FailureDiagnostics.md |
| Provides    | exit code 1 |
| Consumes    | cli.Run, csvdata.Read |

## Purpose

Exit code 1 is the operational-failure code. It is used when the file named on the command line does not exist, is not permitted to be read, or fails while being read. It is distinct from exit 3, which means the file was read but its content was rejected.

## Behavior

- An open or read error from the operating system maps to exit 1, not exit 3.
- Standard output stays empty.
- One diagnostic line naming the file is written to standard error.
- This applies to every invocation form: profile, `--column`, and `--freq`.
- Usage errors (exit 2) take precedence over file access, because argument parsing completes before the file is opened.

# FEATURE: Frequency Mode

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Dispatches `csvstat --freq <name> [--top <n>] <file>` to the frequency listing instead of the profile. |
| Depends On  | FEATURE-FreqLimit.md, FEATURE-UsageErrors.md |
| Provides    | csvstat --freq, csvstat --freq --top |
| Consumes    | freq.Count, freq.Top, cli.ParseArgs |

## Purpose

When `--freq <name>` is given, `cli.Run` writes the frequency listing for that column and never the profile. `--top <n>` limits the rows and defaults to 5. The listing is CSV with header `value,count`, rows ordered by count descending and then value ascending by byte value, using trimmed non-null values only.

## Behavior

- The column name is matched exactly and case-sensitively against the trimmed header.
- A column name absent from the header exits 3 with nothing on standard output and one diagnostic line on standard error.
- Combinations that are usage errors (`--column` with `--freq`, `--top` without `--freq`, a non-positive `--top`) are rejected with exit 2 by the usage-errors story before this dispatch runs.
- Output is built in memory and written to standard output only on success, so a failing command writes nothing to standard output.
- A column with no non-null values writes only the header.
