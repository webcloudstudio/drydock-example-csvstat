## Foundation Contract

The published shape of this foundation. It is built before every other foundation: a web server,
a database, or a CLI is built *into* this tree, this environment, and this test runner. Carried
verbatim into `go_compact.md`.

- source_root: internal/
- test_command: go test ./...
- environment: the module declared in `go.mod`; no vendored toolchain
- dependencies: `go.mod`

```
project/
  go.mod                  # module path; the Go toolchain version
  cmd/                    # one directory per binary, each package main
  internal/               # application packages; not importable outside this module
  bin/                    # launchers; each runs the toolchain, never a vendored copy
```

Application foundations add packages under `internal/`. The generated persistence library is a
separate module at `persistence/`, linked by the root `go.mod`.

### Native application layouts and fixtures

Initialize the root `go.mod` in the language foundation before the DATABASE block.
Use `cmd/app/main.go` for process startup, `internal/cli` for CLI behavior, and
`internal/appserver` for HTTP behavior. The root application module requires
`drydock.local/persistence v0.0.0` with `replace drydock.local/persistence => ./persistence`;
the generated persistence directory owns its nested module. Run both module test suites.

### How do we execute and measure Acceptance Criteria in this language?

An Acceptance Criterion (AC) is an executable check of Blueprint-required behavior. Native tests
use `testing` in `*_test.go`; the project gate is `go test ./...`. Within the existing Blueprint
Python AC container, execute a named test through the shipped helper:

```python
from drydock_go import run_test
result = run_test("./internal/orders", "TestCreateOrder")
assert result.passed, (result.status, result.stdout, result.stderr)
```

Drydock stages this helper beside the criterion. It runs `go test -json -count=1 -run` with an
exact test name, retains output and per-test outcomes, and rejects absent/skipped tests as proof.
The enclosing AC provides identity, timeout, result storage and repair state. Compilation errors
remain distinct from assertion failures in `result.status`. Coverage and persistence observations
require explicit instrumentation per criterion; unavailable observations are unknown.

A criterion that exercises the command line runs the built executable through the same helper,
never `go run`, which reports every non-zero program exit as 1:

```python
from drydock_go import cli_runner
code, out, err = cli_runner("--top", "0", "data.csv")
assert code == 2, (code, out, err)
```

`cli_runner` builds the single `./cmd/<name>` main package once with `go build` and returns
`(exit_code, stdout, stderr)`; pass `package="./cmd/<name>"` when there are several, and `input=`
for standard input. A failed build settles the criterion as `execution-error`.

### How does this language provide the shared persistence contract?

Use the shipped module in `Rigging/languages/go/persistence/`. Drydock copies it to the Target's
`persistence/`, generates `schema.go`, `testing.go` and a schema command from `DATABASE.md`, and
links it into the existing root `go.mod` as `drydock.local/persistence`. Driver versions and sums
are shipped; SQLite uses `go-sqlite3` (a C compiler and CGO are required), PostgreSQL uses `lib/pq`.

Call `persistence.OpenDatabase(ctx, dsn)`, then typed methods such as

## Purpose

`internal/cli` parses arguments with a local `flag.FlagSet` created with `flag.ContinueOnError`,

| Option | Meaning |
|---|---|

| `--freq <name>` | List the most frequent values of the named column. |

4. Names given to `--column` and `--freq` are kept exactly as given; they are matched later,

   which is owned by the rejection story.
2. Standard output starts with the header `column,type,rows,nulls,distinct,min,max,sum,mean,median`,

   name. The remaining fields are produced by the later counts, types, and statistics stories; this
   story establishes the row structure.
3. A quoted field containing a comma is read as one value. A field containing a comma, a double
   quote, or a newline is quoted on output by the `encoding/csv` writer.
4. A file with a header and no data records succeeds with one row per header column.
5. Bytes are compared as bytes: a byte-order mark is not stripped and the file is not rejected for
   invalid UTF-8.
6. Output is written to a buffer and copied to standard output only after reading succeeds.

# FEATURE: Profile Counts

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Report the rows, nulls, and distinct counts for every column of a CSV file. |
| Depends On  | FEATURE-ValueTrimming.md |
| Provides    | profile fields rows, nulls, distinct |
| Consumes    | trimmed header names and values from FEATURE-ValueTrimming.md |

## Purpose

For each column, the profile row carries three counts computed from the trimmed values of that column: `rows`, `nulls`, and `distinct`. Later stories (types, statistics, frequency) reuse the null rule defined here.

## Behavior

- `rows` is the number of data records in the file (the header is not counted). Every column of a file reports the same `rows`.
- A value is **null** when, after trimming, it is empty or equals `NA`, `N/A`, or `NULL` ignoring case. Every other value is non-null.
- `nulls` is the number of null values in the column.
- `distinct` is the number of different non-null values in the column, compared as exact strings after trimming. Comparison is case-sensitive, so `Apple` and `apple` are two values. Null values are never counted.
- A file with a header and no data records reports `rows` 0, `nulls` 0, and `distinct` 0 for every column.
- The null rule is exposed as a single reusable function in `internal/profile` so that types, statistics, and frequency use one definition.
- All counts are computed from the file given. No count is hardcoded.

# FEATURE: Types Date

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Infer the date column type and reject values that are not real calendar dates. |
| Depends On  | FEATURE-ProfileCounts.md |
| Provides    | profile field type value date |
| Consumes    | null rule from FEATURE-ProfileCounts.md |

## Purpose

A column is a `date` column when every non-null value is a real calendar date written `YYYY-MM-DD`. This specification owns the date test; the final type decision is composed in FEATURE-TypesOther.md.

## Behavior

- A value qualifies when, after trimming, it is exactly ten characters, matches `YYYY-MM-DD` (four digits, `-`, two digits, `-`, two digits), and names a real calendar date.
- A value such as `2025-02-30`, `2025-13-01`, or `2025-00-10` does not qualify. `2024-02-29` qualifies (leap year); `2025-02-29` does not.
- One non-qualifying non-null value makes the column not `date`; the column then falls through to the next type in order.
- Null values never disqualify the type.
- A column of integers or numbers is typed by FEATURE-TypesNumeric.md before the date test applies; a date value never matches the integer or number patterns.
- Implementation uses `time.Parse` with layout `2006-01-02` plus a length check so that non-padded forms such as `2025-2-3` are rejected.

# FEATURE: Types Numeric

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Infer the integer and number column types from the non-null values of a column. |
| Depends On  | FEATURE-ProfileCounts.md |
| Provides    | profile field type values integer and number |
| Consumes    | null rule from FEATURE-ProfileCounts.md |

## Purpose

A column's type is the first type in the order integer, number, date, boolean, text that every non-null value satisfies. This specification owns the first two members of that order.

## Behavior

- `integer`: every non-null value matches `-?[0-9]+` (the whole value, after trimming).
- `number`: every non-null value matches `-?[0-9]+(\.[0-9]+)?` (the whole value, after trimming) and the column is not `integer`.

- A single non-matching non-null value disqualifies the type for the column.
- Null values (see FEATURE-ProfileCounts.md) never disqualify a type.
- Leading zeros are permitted (`007` is an integer). Arbitrarily long digit strings are integers; no length limit applies.
- Matchers live in `internal/profile` and are hand-coded or use `regexp` anchored with `^` and `$`.

# FEATURE: Median

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Report the exact median of the non-null values of integer and number columns. |
| Depends On  | FEATURE-TypesNumeric.md, FEATURE-MinMax.md |
| Provides    | profile field median |
| Consumes    | column type decision, null rule, trimmed values |

## Purpose

The `median` field of a profile row gives the middle of a numeric column's distribution. It is
computed from exact values so ordering and the even-count average are never subject to floating
point error.

## Trigger

Every profile run computes `median` for every column whose inferred type is `integer` or `number`.

## Behavior

- Only non-null values participate (null: empty, `NA`, `N/A`, `NULL` ignoring case, after trimming).
- Values are parsed into `big.Rat` and sorted ascending by exact value (`Rat.Cmp`).
- With an odd count the median is the middle element.
- With an even count the median is the mean of the two middle elements, as an exact `big.Rat`.
- Both integer and number columns write the median through the decimal formatter, with exactly two
  decimals (see `FEATURE-DecimalFormat.md`).
- A column of type `text`, `date`, `boolean`, or `empty` leaves `median` blank.
- Input order does not matter; the column is sorted on a copy so no other statistic is disturbed.

## Reads

- The trimmed, null-classified values of the column and its inferred type.

## Writes

- The `median` cell of the profile row on standard output. No files, no persistence.

## Programmatic Acceptance

The `sum` and `mean` fields of each profile row summarize numeric columns. They are computed with
exact arithmetic so that no digit string overflows and no binary floating point error enters the
result. Rounding happens once, when the value is written (see `FEATURE-DecimalFormat.md`).

## Trigger

Every profile run (`csvstat <file>` and `csvstat --column <name> <file>`) computes `sum` and `mean`
for every column whose inferred type is `integer` or `number`.

## Behavior

- Package: `internal/profile` accumulates, `internal/decimal` holds exact values.
- Only non-null values participate. Null values (empty, `NA`, `N/A`, `NULL` ignoring case, after
  trimming) are skipped.
- Each value is parsed exactly: an integer into `big.Int`, a number into `big.Rat` through
  `Rat.SetString`. `float32` and `float64` are never used on the data path.
- `sum` is the exact total of the non-null values.
- `mean` is the exact total divided by the count of non-null values, held as a `big.Rat`.
- An `integer` column writes `sum` as a plain integer (an arbitrary-precision digit string). Its
  `mean` is written by the decimal formatter.
- A `number` column writes `sum` and `mean` through the decimal formatter.
- A column of type `text`, `date`, `boolean`, or `empty` leaves `sum` and `mean` blank.
- Columns are independent: a numeric column's sum never depends on another column.

## Reads

- The trimmed, null-classified values of the column and its inferred type.

## Writes

- The `sum` and `mean` cells of the profile row on standard output. No files, no persistence.

# FEATURE: Decimal Format

| Field       | Value |
|-------------|-------|
| Version     | 20261025 V1 |
| Description | Write numeric statistics with exactly two decimals, rounded half away from zero once from the exact value. |
| Depends On  | FEATURE-SumMean.md, FEATURE-Median.md |
| Provides    | decimal formatter for min, max, sum, mean, and median |
| Consumes    | exact big.Rat values from sum, mean, median, min, max |

## Purpose

Numeric statistics are written in one canonical shape. Rounding is performed exactly once, at
output, from the exact rational value, so that results are reproducible and independent of
binary floating point.

## Trigger

Every profile row of an `integer` or `number` column writes its numeric cells through this
formatter.

## Behavior

- Package: `internal/decimal` exposes a function taking a `*big.Rat` and returning a string.
- For a `number` column: `min`, `max`, `sum`, `mean`, and `median` are two-decimal strings.
- For an `integer` column: `mean` and `median` are two-decimal strings; `min`, `max`, and `sum`
  are plain integers with no decimal point.
- Two-decimal form: scale the absolute value by 100, round half up on the absolute value
  (ties move away from zero) using `big.Int` arithmetic, then insert the decimal point. There is
  always at least one digit before the point and exactly two after it.
- A leading `-` appears only when the rounded result is non-zero and the value is negative. A
  negative value that rounds to zero is written without a sign.
- No thousands separator, no exponent, no leading `+`.
- Rounding is applied once to the exact value; an already rounded value is never rounded again.
- Non-numeric column types are unaffected and keep their own rules.

## Reads

- Exact `big.Rat` values produced by the sum, mean, median, and min/max computations.

## Writes

- The numeric cells of the profile row on standard output.
